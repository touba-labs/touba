# Touba 1.4.0

## Executive Summary

This candidate adds consumer-owned package governance. An application keeps
its approval requirements when a dependency changes, while preparation presents
contract changes for review. Runtime and both SDKs share version 1.4.0.
Publication follows native qualification and maintainer approval.

## Added

- Persistent `configuration.package_contracts` and `configuration.tool_policies`
  in the consuming project, with exact-digest review through `review_packages`.
- Binding-level `approval_policy`, combined with the tool declaration before
  execution. Compatible requirements use one operation approval.
- Verified package name, version, content digest and lock provenance in traces,
  correlated with approval requests, calls and effects.

## Changed

Inspection and Explorer show tool and checkpoint policies, including effective
requirements and their source/application origins. Approval signer references
are pseudonymized per run; only the required attested role is included.

## Fixed

- Removing a dependency's approval requirement cannot silently remove the
  application's retained minimum, including after remove/add or build cleanup.
- Package admission failures retain their precise code through CLI, JavaScript
  process/persistent and Python synchronous/asynchronous APIs.
- macOS Python sandbox loading can enumerate selected code directories without
  granting recursive reads of adjacent project files.

## Security And Governance

Preparation compares approval, role, deadline, signer separation, capability,
secret, memory-access and signature requirements. Changed contracts require
explicit review of the exact package digest. Reviewing an update preserves the
consumer minimum; changing that minimum is a separate host decision.
Conflicting roles require resolution. Approval grants no additional authority.
An old approval cannot be resumed against a newly admitted package snapshot.

## Breaking Changes

The new configuration and manifest fields require the matching toolchain.
Older tools reject them. Existing prepared projects require an explicit
preparation step to adopt their package policies. Applications matching generic
engine errors should handle the documented package admission diagnostics.
Existing suspended executions stay with their original build and state stores.

## Migration

1. Preserve project configuration, state stores and the existing toolchain for
   suspended runs. Reconcile them before upgrading the application.
2. Install the qualified 1.4.0 candidate and matching JavaScript/Python SDKs in
   an isolated copy of the project.
3. Run `touba prepare --mode plan`, review the initial policy adoption, then
   `touba prepare --mode write`. Preserve `configuration.package_contracts` and
   `configuration.tool_policies` in version control.
4. For a changed dependency contract, review its diff and select the exact
   digest with `review_packages` in host decisions. Re-run preparation with
   that decision file. Choose any consumer-policy change explicitly.
5. Run `touba prepare --mode check` and exercise the application workflow.

For direct AIR execution through an SDK, supply the prepared manifest or an
equivalent binding policy. An AIR alone does not identify a project to load.

## Validation Evidence

Source tests cover retained approvals, semantic review, generic export and
deployment fixtures, tampered package refusal, both SDK transports, HTTP
pause/resume, SQLite/export and concurrent trace correlation. Native archive
and editor results are recorded separately against exact candidate digests.
The archived 1.3.1 release remains unchanged.

## Known Limits

Trusted handlers keep their operating-system account's access. Use explicit
required confinement and scoped grants for untrusted handler execution.
Windows native confinement remains deferred. Business correctness and
cross-run service idempotence belong to application services. Without a
preserved project baseline, first adoption cannot reconstruct older policies.
Pseudonymized signer references still require appropriate access and retention.
